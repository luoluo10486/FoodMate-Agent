# FoodMate 前端与后端接口闭环执行计划

> 制定日期：2026-09-15
> 适用范围：`foodmate-ui` 前端、`foodmate-api`/Application 后端接口消费者，以及 Figma 视觉落地。
> 当前原则：Figma 是颜色、字体、布局、组件状态和交互的视觉来源，但不要求页面像素级一比一；本计划不执行 105 个画板全量像素差异，也不执行花瓣像素对比。

## 1. 总目标

完成 FoodMate 的真实前端业务闭环：后端已经存在的浏览器接口都必须有明确的前端 service、页面入口、状态处理和测试证据；后端内部接口保留在内部契约矩阵中，不强行暴露给浏览器。

当前代码扫描口径为：

- Controller 方法级映射 `126` 个。
- 浏览器可关联接口 `119` 个。
- Java/Python Runtime、Outbox、健康探针等内部接口 `7` 个。
- 逐条接口清单以《前后端接口覆盖矩阵》和《前端接口覆盖清单》为唯一登记来源，不以“Controller 存在”或 Fixture 页面展示作为完成依据。

“后端已完成”需要区分两个层次：

1. **代码契约完成**：路由、DTO、错误码、鉴权、角色、幂等键、revision 和状态迁移可以从代码和定向测试确认。
2. **运行环境完成**：真实数据库、Redis、RocketMQ、MinIO、Milvus、Python Runtime、Cookie/CSRF 和部署配置在目标环境联调通过。

本轮前端闭环以第一层为开发门槛；第二层必须按环境单独验收，不能用前端组件测试代替。

## 2. 设计与实现边界

### 2.1 Figma 使用方式

- 读取对应 Figma 页面获取布局层级、颜色、字体、间距、圆角、组件状态和交互意图。
- 允许根据真实数据长度、响应式宽度、可访问性和后端字段对布局做合理适配。
- 颜色、字体和状态优先沉淀为语义 Token，再由页面和 `src/components/ui` 使用。
- 页面验收采用少量代表路由的浏览器运行检查、关键状态截图和人工视觉复核，不建立“看起来接近”以外的伪精确指标。
- 不因视觉差异创建虚构后端字段、虚构 iconfont glyph 或伪造交互成功。

### 2.2 UI 基础设施

- 页面控件统一从 `foodmate-ui/src/components/ui` 引入 shadcn/Radix 封装。
- 页面和业务组件不直接声明原生交互控件、不直接引入 `@radix-ui/*`，不重新依赖 `AdminPrimitives`。
- Lucide 继续承担通用命令图标。
- iconfont 在实体字体包、CSS/Unicode 映射、来源、版本、SHA-256、许可证和授权范围齐全前保持 `BLOCKED`；不得创建虚构 `@font-face` 或映射。

### 2.3 真实模式原则

- `VITE_AGENT_MODE=real` 下不使用 Fixture 成功结果覆盖接口失败、空数据或处理中状态。
- HTTP 接受响应不直接等同于业务终态；异步任务必须读取服务端状态或订阅 SSE。
- 写操作成功后以服务端重新读取结果为准，不能只用本地乐观状态宣告成功。
- 页面卸载、会话切换、条件切换和用户取消必须取消读取、轮询和 SSE 连接，并阻止迟到响应写回。
- 后端不支持的业务状态不能由前端自行新增；失败原因和 retryable 能力只使用服务端返回事实。

## 3. 当前基线

已具备并有代码或测试证据的范围：

- Auth、用户资料、设备会话、头像和账户导出/删除的真实 service 与页面入口。
- Workspace、Session、Message、Memory、ChatRun、AgentRun、Approval 和 SSE 的真实页面消费者。
- Diet Records、Intake Analysis、Meal Planning、Knowledge、Profile 的主要读写路径和请求生命周期保护。
- Admin Overview、Users、Runs、Tools、Knowledge、Retention、Usage、Model Governance、Operation Audit 和 Deleted Resources 的主要真实页面入口。
- shadcn 控件边界、错误码映射、分页、请求取消、旧响应隔离和服务端刷新已经形成可复用模式。
- 本轮 Admin 删除资源、模型治理读取和操作审计导出生命周期收口后，前端门禁与后端定向测试均通过。

仍需持续收口的不是“再造一套后端”，而是：

- 按矩阵逐条检查每一个浏览器接口的页面行为是否完整。
- 对尚未有真实环境证据的接口执行受控本地联调。
- 对 Figma 页面进行分域视觉适配和代表状态复核，而不是全量像素对比。
- 完成真实失败、空态、无权限、冲突、取消、轮询和重连状态的用户可读反馈。

## 4. 分阶段执行计划

### 阶段 0：冻结基线与接口台账

**目标**：保证后续工作不会漏掉后端接口或把历史 Fixture 当成真实闭环。

**工作项**：

- 从 `foodmate-api` Controller 重新扫描方法级映射。
- 与《前后端接口覆盖矩阵》逐行比对路径、方法、DTO、角色、错误码和状态。
- 为每一行补齐页面入口、service 方法、状态证据、后端测试和最后验证提交。
- 将接口状态统一为 `REAL_CONNECTED`、`SERVICE_ONLY`、`FIXTURE_ONLY`、`INTERNAL` 或 `BLOCKED`。

**完成门槛**：`126/126` 映射有登记；`119` 个浏览器接口都有下一步说明；`7` 个内部接口明确不属于浏览器页面范围。

**当前状态**：已建立并持续维护，后续批次只允许校准事实，不允许删掉未完成项。

### 阶段 1：按业务域收口真实页面消费者

每个接口都按以下顺序处理：

1. 读取后端 Controller、request/response DTO、错误码、鉴权和测试。
2. 在 `src/services` 建立或校准唯一 service 方法，统一走 `apiClient` 或 `sseStream`。
3. 把 service 接入真实页面入口，禁止在 real 分支回退到 Fixture。
4. 覆盖加载、空数据、失败、重试、无权限、冲突、处理中和成功刷新。
5. 对读取补充 AbortController、请求序号和卸载保护；对写入补充确认、幂等键、revision 和服务端回读。
6. 添加前端定向测试和受影响后端定向测试。
7. 更新三份接口文档后再进入下一个域。

固定顺序如下：

| 顺序 | 业务域 | 主要接口范围 | 交付重点 |
| --- | --- | --- | --- |
| 1 | Auth 与 Account | `/api/auth/**`、`/api/users/me/**` | 登录错误码、会话恢复、头像、资料保存、导出、删除和账户状态 |
| 2 | Workspace 与 Chat | `/api/sessions/**`、消息、ChatRun | 会话分页、首条消息、消息历史、HTTP 接受与 SSE 终态分离 |
| 3 | Agent 与确认 | `/api/agent-runs/**`、审批和 Proposal/Result | 取消、重试、预算追加、恢复、写入确认、反馈、重连和去重 |
| 4 | Diet 与 Analysis | 饮食记录、删除恢复、营养目录、复合菜、分析 | 日期/周视图、单位、营养候选、失败清空和服务端事实 |
| 5 | Meal Planning | `/api/meal-plans/**`、购物清单和进度 | revision、幂等、计划切换、购物清单生成和状态刷新 |
| 6 | Knowledge | 知识检索、上传、批次、发布、重试、重索引和 SSE | 引用安全字段、批次终态、过期、重试和权限 |
| 7 | Profile | Profile、Memory、设备会话 | 长期记忆确认/修改/删除、摘要失效和身份清理 |
| 8 | Admin | 查询、用户、Runs、Tools、DLQ、Retention、Usage、Audit、Model Governance | 最小权限、确认状态机、导出轮询、失败重试和服务端回读 |

**完成门槛**：矩阵中每个浏览器接口都至少有一个真实页面消费者或有明确的 `SERVICE_ONLY` 阻塞理由；不能以“service 方法存在”代替页面闭环。

### 阶段 2：Admin 高风险操作与异步任务收口

重点处理需要服务端事实确认的页面操作：

- 软删除资源恢复：真实模式不本地删除行，恢复后重新读取服务端列表。
- 模型供应商状态、价格和预算：保留角色、revision、确认摘要和幂等键，成功后重新读取治理数据。
- 操作审计导出：区分 `queued`、`running`、`completed`、`failed`、`expired`、`download_consumed`；轮询结束或组件卸载时清理定时器和请求。
- Retention、DLQ、Knowledge 重索引和其它高风险操作：继续使用统一确认状态机，不将接受响应包装成业务成功。

**完成门槛**：每个写操作都有权限、确认、重复点击、失败、取消、服务端刷新和后端定向测试证据；禁止用本地更新替代服务端结果。

### 阶段 3：Figma 视觉适配与 shadcn 页面迁移

按 Auth → Workspace/Chat → Diet/Analysis/Planning → Knowledge/Profile → Admin 顺序执行。

每页执行：

- 先读取对应 Figma 节点的布局和状态，不从旧页面 CSS 反推新设计。
- 把颜色、字体、间距、圆角、阴影、边框和状态写入语义 Token。
- 用 `src/components/ui` 重组 Button、Input、Select、Dialog、Tabs、Tooltip、Table、Alert 等控件。
- 保留真实后端字段和状态，不为了追求视觉相似删除错误、加载、空态或权限信息。
- 只做桌面、移动和一个窄视口的代表性浏览器检查，重点查看文字可读性、头像一致性、溢出、控件可访问性和状态切换。

**完成门槛**：页面视觉结构与 Figma 意图一致，文字可读，真实数据长度不破坏布局；不以像素差异百分比作为通过条件。

### 阶段 4：受控后端联调

后端核心代码目前已经有较完整的业务实现和定向测试，但“代码通过”不等于“目标环境联调完成”。本阶段只做受控、可回收的本地验证：

- 启动必要的 Java、Python Runtime、PostgreSQL、Redis、RocketMQ、MinIO 和 Milvus 依赖。
- 从登录开始验证一条代表性真实链路：创建 Session → 发送消息 → AgentRun → SSE → 终态 → 页面刷新。
- 对饮食记录、餐食计划、知识检索、Admin 查询和一个高风险写操作各执行一条成功路径及一条稳定失败路径。
- 回读数据库/服务端状态，确认幂等、revision、权限、SSE 游标和错误码没有被前端误读。
- 不执行生产压测、长稳、破坏性故障注入、真实硬删除或发布操作。

**完成门槛**：只把实际运行过的接口标记为环境联调通过；未启动外部依赖的测试只能标记为代码契约通过。

### 阶段 5：小范围交付验收与文档收尾

- 每个阶段只运行受影响模块的定向测试。
- 交付前运行一次前端 `test`、`typecheck`、`lint`、`format:check`、`build` 和 `git diff --check`。
- 后端只运行受影响模块测试和必要的 `mvnw.cmd verify`；不为单个页面重复做全量重型测试。
- 浏览器只检查代表性路由和关键状态，不采集 105 个画板全量 PNG/diff。
- 更新《前端接口覆盖清单》《前端已完成实现清单》《前后端接口覆盖矩阵》，只记录真实命令、测试数量和已知边界。
- 每个大点单独提交，提交前检查工作区没有临时截图、缓存或未登记生成物。

## 5. 每个接口的统一验收清单

- [ ] HTTP/SSE 方法、路径、请求字段和响应字段与后端 DTO 一致。
- [ ] 鉴权、角色、CSRF、幂等键、revision 和错误码没有被前端绕过或改名。
- [ ] 有真实 service 方法和页面入口；real 模式没有 Fixture 成功回退。
- [ ] 有加载、空数据、失败、重试、无权限、冲突、取消和处理中状态。
- [ ] 读取请求支持取消、旧响应隔离和卸载清理。
- [ ] 写操作以服务端重新读取结果为准，不本地伪造成功。
- [ ] SSE 使用 `Last-Event-ID`、`sse_event_id` 去重，并在终态关闭连接。
- [ ] 前端定向测试和后端受影响测试已执行并记录。
- [ ] 矩阵、完成清单和接口覆盖清单已同步。

## 6. 明确不纳入本轮完成门槛的内容

- 105 个 Figma 画板全量像素级差异、全量 PNG 采集和花瓣像素对比。
- 生产级吞吐、P95/P99、长时间运行、完整依赖故障矩阵和多实例扩容。
- 生产部署、CI/CD、灰度、回滚、备份恢复和安全演练。
- 未经用户单独授权的数据库硬删除、对象存储删除或向量索引清理。
- iconfont 实体包、CSS/Unicode 映射、来源、版本和许可证缺失时的任何代码补齐。

## 7. 下一步执行顺序

1. 收口并提交当前 Admin 删除资源、模型治理和操作审计生命周期批次。
2. 按矩阵重新扫描剩余 `SERVICE_ONLY` 或状态证据不完整的浏览器接口，优先处理真实页面仍缺状态的条目。
3. 逐页执行 Figma 视觉适配和 shadcn 控件统一，先完成 Auth、Workspace/Chat，再进入业务页和 Admin。

5. 最后做一次小范围代表路由验收和文档收尾；iconfont 保持 `BLOCKED`，直到资料完整。
