# 非生产业务能力完善执行计划

## 1. 目标与边界

本计划用于完成 FoodMate 在本地开发环境和秋招演示场景下的业务能力完善。目标是让真实业务数据、Agent 编排、知识库、记忆、营养检索、SQL Agent、管理端和前端体验形成一致、可复现、可解释的闭环。

本计划不把以下内容作为完成门槛：

- 生产级吞吐、P95/P99、容量规划和长时间压测。
- Java、Python、PostgreSQL、Redis、RocketMQ 的完整故障注入矩阵。
- Kubernetes、staging/production、CI/CD、灰度发布和发布回滚。
- 数据库备份恢复、跨节点容灾和生产级监控平台。
- 多实例扩容、队列积压 SLO、账单对账和供应商长期稳定性。

测试只服务于业务正确性。每完成一个大功能点，集中执行受影响模块的定向业务测试，再提交 Git；不为小改动重复运行全量测试。

## 2. 当前基线

已具备的能力：

- 用户、会话、消息、AgentRun、SSE、Java/Python 双运行时和 RocketMQ 主链路。
- 饮食记录、营养分析、餐食计划、购物清单和写确认。
- `calculator`、`time_parser`、`knowledge_search`、`database_query`、`food_log_writer`、`plan_validator`、`meal_plan.save_plan` 七个正式工具。
- 公共知识库批量上传、PDF/DOCX/Markdown/TXT 解析、Redis Stub/Milvus 索引、显式发布和引用。
- PostgreSQL 中 1,000 条 USDA 食材和 1,518 条单位换算；独立营养 Milvus 集合保留 1,000 条向量。
- SQL Agent 只读查询、权限过滤、AST Guard、SQL 审计和真实 Chat 单次业务闭环。
- 短期消息上下文、Session 摘要、长期记忆候选和用户记忆管理接口。

已知缺口：长期记忆候选仍采用可解释的本地规则，不做模型推断；营养目录缺少更完整的中文业务映射；部分管理页面仍需真实接口核对。K1 已重新导入 9 份正式公共资料并完成 local-stub 业务闭环；K2 已更新知识切分和关键词检索代码，D170 已将正式批次按 K2 规则完成 `stub + Redis` 重索引，真实 Embedding/Milvus 仍待授权。

## 3. 实施顺序

实施顺序固定为：

```text
真实业务数据
  -> 知识库内容与检索质量
  -> 记忆与上下文质量
  -> 营养语义候选与饮食业务
  -> SQL Agent 业务覆盖
  -> 管理端和前端真实接口收口
  -> 全链路业务回归与文档收尾
```

依赖关系：知识库内容先于 RAG 质量；记忆结构先于记忆检索优化；营养候选先于饮食记录中的模糊食材匹配；后端契约核对先于前端收口。

## 4. K1 真实公共知识库内容建设

### 4.1 内容范围

建立首批可演示的公共知识目录，至少包含：

- 平衡膳食和宏量营养素基础。
- 常见食材的营养特点、适用烹饪方式和保存方法。
- 早餐、午餐、晚餐和加餐的搭配原则。
- 控盐、控糖、增加蛋白质、增加膳食纤维等通用饮食主题。
- 食品安全、熟食保存和备餐卫生基础。

每份文档必须有标题、来源名称、来源版本、授权说明、适用范围和更新时间。数据只进入公共知识库，不把用户饮食记录复制为知识文档。

### 4.2 导入与质量门禁

- 使用正式 PDF、DOCX、Markdown 或 TXT 文件导入。
- 每份文档先做 UTF-8、文件签名、空文档、外链、宏、脚本和基础 PII 校验。
- 文档导入后保持 `draft`，索引成功后仍需要管理员显式发布。
- 发现重复文档时按来源、版本和内容摘要去重；新版本不覆盖旧版本，发布后再切换当前版本。
- 不在本阶段重新调用真实 Embedding，除非用户明确确认；先允许 stub/local deterministic 运行验证业务链路。

### 4.3 完成标准

- 至少导入 8 至 12 份内容不同的正式知识文档。
- 每份文档均完成索引、状态查询和显式发布。
- 检索结果能返回标题、版本、章节路径、chunk ID 和安全片段。
- 下线后不可被检索，新版本发布后旧版本不再成为当前版本结果。

## 5. K2 知识切分和检索质量完善

当前 `chunk_markdown` 已实现标题识别和最多 900 字符切分。本阶段在保持现有稳定 `embedding_id` 规则的前提下完善切分策略。

### 5.1 切分策略

- Markdown：按标题层级保留 section path，再按段落切分。
- PDF/DOCX：先恢复段落和标题，再进入同一切分器。
- 优先按段落边界切分，避免在句子中间截断。
- 使用 Token 或字符双重上限，默认目标 500 至 800 字符，硬上限 1,000 字符。
- 相邻 chunk 保留少量语义重叠，避免跨 chunk 丢失上下文。
- 每个 chunk 保存文档版本、章节路径、序号、ACL 和来源元数据。
- 表格先按“表名/列名/行语义”转成文本；复杂扫描表格仍保留为后续能力，不作为本阶段门槛。

### 5.2 检索策略

- 先过滤 `tenant_id=0`、`public_published`、`published`、`indexed`、当前版本和未删除。
- 召回最多 12 个候选，重排最多 6 个，最终最多 4 条引用。
- 每个文档最多贡献 2 条引用。
- 关键词检索用于标题、别名和精确术语；向量检索用于语义扩展。
- 无证据或证据不足时明确返回无命中，不生成伪引用。
- 引用只保留安全片段，不返回对象存储地址、对象键和完整原文。

### 5.3 完成标准

- 增加切分单元测试和 5 至 10 个固定检索样例。
- 检查标题命中、同义词命中、跨段落语义命中、无命中和下线过滤。
- 检查重复索引不重复产生 chunk/vector。
- 检查 stub 与 local deterministic 返回相同的 ACL 和引用约束。

## 6. K3 结构化记忆与上下文完善

截图中的数据库记忆思路适用于 `user_memories`，但不能替代饮食记录、营养目录和餐食计划等领域表。

### 6.1 数据边界

- `food_logs`：饮食事实。
- `meal_plans`：餐食计划事实。
- `nutrition_foods`：营养目录事实。
- `session_summaries`：当前会话的压缩视图。
- `user_memories`：跨会话仍有价值的偏好、习惯和交互规则。

### 6.2 记忆候选

- 保留 Python 只生成候选、Java 负责校验和写入的边界。
- 增加明确表达样例：喜欢、不喜欢、忌口、烹饪能力、预算和用餐时间偏好。
- 一次性参数、完整计划、营养目标、医疗事实和工具审批不进入普通长期记忆。
- 继续执行来源消息、用户归属、置信度、冲突、TTL 和敏感信息校验。
- 相同 `memory_type + memory_key` 进入更新或冲突流程，不无限追加。

### 6.3 上下文装配

- 最近 8 条有效消息继续保留。
- 摘要固定保存 goals、constraints、decisions、open_questions 和来源消息 ID。
- 已确认、未过期、未删除的长期记忆才可进入 AgentRun。
- 按意图筛选记忆类型：planning、cooking、record、nutrition 使用不同白名单。
- Trace 只保存来源 ID、digest 和安全摘要，不复制完整记忆正文。

### 6.4 完成标准

- 通过喜欢、不喜欢、预算、烹饪能力、一次性请求、冲突和删除场景的业务测试。
- 用户删除或修改记忆后，下一次 AgentRun 不再使用旧内容。
- 过期记忆不参与冲突判断和 Context 注入。
- 更新记忆后关联摘要失效并重建。

### 6.5 K3 当前交付（2026-09-06）

- Python 使用确定性规则将喜欢、不喜欢/忌口、预算、烹饪能力、用餐时间和回答偏好转换为短结构化候选；候选只携带来源消息 ID，不保存整句请求、回答或 Prompt。
- 一次性请求、完整计划、营养目标和医疗/高影响健康事实不会生成或通过 Java 校验；`plan` 不再属于新的长期记忆白名单。
- Java 对同一 `memory_type + memory_key` 做事务内读取和 PostgreSQL advisory lock：相同 JSON 视为重复事实不再新增；不同值进入 `conflict`，用户确认后同 key 其他活动值转为 `rejected`。
- 手动修改要求 JSON 对象且重新执行长期记忆安全校验；修改、删除和冲突确认都会使用户会话摘要失效。ContextBuilder 继续执行意图类型白名单、确认状态、最多 8 条和重复 key 防护。
