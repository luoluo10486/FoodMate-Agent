# M1-5 核心饮食业务与写确认实施方案

更新时间：2026-08-13

## 1. 文档目的

本文把 M1-5 的已确认决策固化为实现前的单一实施口径。它约束饮食记录、营养目录、营养分析、餐食计划、购物清单和写操作确认的范围、数据模型、接口语义、事务边界与验收门槛。

本文同时作为 M1-5 的实施口径和当前状态记录。第一切片已完成 Java application、infra、api、迁移脚本和本地 HTTP E2E；Java 仍不在启动时自动建表、迁移或回滚。V13/V14 的数据库结构已在当前本地 `FoodMate` 库中经只读校验确认，原始执行人和历史执行时间若未记录不得补写。

发生冲突时，按 [文档索引](../文档索引.md) 的优先级判断当前事实；本文顶部状态和“当前实现状态”小节描述已验证事实，后续章节描述目标和剩余实现。历史归档中的页面或 mock 完成记录只代表视觉/交互交付，不代表真实业务闭环。

## 2. 范围和明确不做项

### 2.1 本轮范围

1. 手工饮食记录真实闭环：Java API -> PostgreSQL -> 营养目录匹配与确定性计算 -> 查询和日报汇总；当前已完成无目录数据时的 `pending` 分支，真实目录匹配仍待 seed。
2. 饮食记录的创建、编辑、软删除、恢复、查询，以及幂等、并发版本和操作审计。
3. 营养目录、别名、分类、单位换算、来源版本和营养快照。
4. 当天、最近 7 天、最近 30 天的营养分析，包含目标对比、数据覆盖率和不完整提示。
5. 单用户、1-7 天、早餐/午餐/晚餐的餐食计划；支持人数、预算、热量目标、蛋白质目标、忌口和过敏原。
6. 由已保存计划生成购物清单。
7. Agent 提案和自然语言写操作的确认事实、过期、拒绝、执行、失败、幂等和审计；当前只实现 `meal_plan.save_plan` 的提案/确认/执行切片。
8. 本地双 Java JVM 压测、吞吐基线和 Java/Python/PostgreSQL/Redis/RocketMQ 重启恢复验证。
9. Java Actuator liveness/readiness 和本地基础 metrics；日志至少关联 `request_id`、`trace_id`、`run_id`。

### 2.2 当前明确不做

- 不建立 Kubernetes、staging/production 两套环境、云资源或发布平台。
- 不把本地验证结果当作生产容量、生产可用性或云模型长期稳定性结论。
- 不在本轮做真实云模型长期稳定性、供应商价格/账单审计；这些在本地链路稳定后单独测试。
- 不在本轮做 Prometheus、Grafana、OpenTelemetry、ELK 等完整生产监控栈。
- 不在本轮做 `pg_dump`、独立恢复库、灾备切换、数据损坏恢复或备份保留策略；数据库备份暂不纳入。
- 不允许 Python、模型或检索内容直接写业务表、直接确认或直接执行 Tool。
- 不使用模型临时估算营养数值，也不凭空生成 USDA 数值或许可证结论。
- 暂不规范化 `meal_plans`、`shopping_lists` 的 JSON 细节；对应功能实现前只保持当前基线结构，并以本文状态约束为准。
- 不支持多人复杂营养目标、周期循环、实时价格库存、医疗诊断或治疗建议。

## 3. 实现顺序

```text
文档统一
  -> 手工记录 schema/API/事务
  -> 营养目录和确定性计算
  -> 查询与日报分析
  -> 餐食计划校验/保存
  -> 购物清单
  -> Agent 提案和确认接入同一写入服务
  -> 本地压测与故障恢复
```

手工录入和 Agent 写入必须共用同一套 Java application 用例、领域校验、Repository、事务、幂等和审计逻辑，不创建第二套 Agent 专用写入逻辑。

## 4. 饮食记录数据模型

当前没有历史数据，因此直接修改基线表，不保留旧 JSON 兼容字段。

| 字段 | 类型 | 说明 |

## 5. 营养目录和单位换算

### 5.1 数据落点

营养目录使用 PostgreSQL 表，不写死在 Java 代码中，也不由模型直接返回热量、蛋白质、脂肪和碳水数值。建议表为：

- `nutrition_foods`：食材标准名称、中文名称、别名、分类、来源、版本、每 100g/100ml 的营养基准值、审核状态。
- `nutrition_unit_conversions`：食材级单位换算，例如某食材“1 个”对应多少克，包含规则来源和版本。

基础来源采用 USDA FoodData Central Foundation Foods / SR Legacy。FoodMate 负责中文名称、别名、分类、单位换算、来源版本和人工复核。当前仓库没有实际 USDA 数据文件，实施时必须核实官方数据版本、许可证和具体数值，不能凭空写种子数据。

### 5.2 首批目录

首批只引入约 20-30 个高频食材，验证通过后再扩展到 100-200 个。首批优先支持 `g/ml`；“个、碗、勺”等单位只有存在明确的食材级换算规则时才转换。

种子数据采用版本化人工 SQL，例如 `script/sql/FoodMate/seed/V1__nutrition_usda_seed.sql`。Java 不在启动时自动执行种子 SQL，SQL 必须人工执行、校验并记录版本。

### 5.3 计算规则

```text
每项营养 = 标准化份量 / 100 * 目录中每 100g（或 100ml）的营养值
餐次汇总 = 所有 nutrition_status = matched 的明细快照求和
```

无法匹配名称或无法安全换算单位时，保存原始记录，标记 `pending`，不使用模型估算补值。报告必须显示覆盖率，例如 `3/4 项已估算`，并显示“数据不完整”。

## 6. 数值精度

- PostgreSQL 营养和份量字段使用 `NUMERIC`，避免浮点二进制误差。
- Java 使用 `BigDecimal`，禁止使用 `double` 参与营养计算。
- 份量使用 `NUMERIC(12,3)`；每 100g/100ml 基准值和营养快照使用 `NUMERIC(12,4)`。
- 计算过程保留 4 位小数；API 和报告展示时四舍五入到 2 位。
- `NUMERIC` 是 PostgreSQL 的精确十进制定点数类型；括号内的两个数字分别表示最大精度和小数位数，例如 `NUMERIC(12,4)` 最多 12 位数字，其中 4 位在小数点后。

## 7. 写操作确认

### 7.1 确认范围

Agent/自然语言提案产生的新增、修改、删除、恢复和保存计划都必须经过确认。用户在页面中主动填写并点击保存，视为明确意图，可以直接提交；删除和恢复仍需二次确认。

Python、模型输出和检索内容不能自行确认。确认事实绑定用户、资源、操作类型、参数摘要、`request_id`/`trace_id` 和过期时间；参数变化后旧确认立即失效。

### 7.2 `approval_requests`

新增独立确认事实表 `approval_requests`，建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `approval_request_id` | `BIGINT` | 主键 |
| `user_id` | `BIGINT` | 确认用户 |
| `session_id` / `agent_run_id` | `BIGINT` nullable | 来源上下文 |
| `resource_type` / `resource_id` | `VARCHAR` / `BIGINT` nullable | 资源绑定 |
| `operation` | `VARCHAR(64)` | create/update/delete/restore/save_plan |
| `parameters_digest` | `VARCHAR(128)` | 参数摘要 |
| `status` | `VARCHAR(32)` | pending/confirmed/rejected/expired/executed/failed/superseded |
| `expires_at` | `TIMESTAMPTZ` | 过期时间 |
| `confirmed_at` / `executed_at` | `TIMESTAMPTZ` nullable | 状态时间 |
| `idempotency_key` | `VARCHAR(128)` | 确认幂等键 |
| 审计字段 |  | request/trace/操作者等 |

确认、业务写入、工具结果和 `operation_audits` 必须在同一事务内完成。相同确认/幂等键不能重复执行；已执行确认重放返回第一次结果。

### 7.3 幂等和并发

- 所有创建、编辑、删除、恢复写接口统一要求 `Idempotency-Key`。
- 编辑、删除、恢复必须携带 `revision`；不一致返回冲突，不覆盖他人修改。
- 相同幂等键和相同参数重复请求返回第一次结果；相同幂等键但参数不同返回幂等冲突。
- 网络重试必须复用原幂等键。

## 8. 营养分析

第一版支持当天、最近 7 天、最近 30 天；指标为热量、蛋白质、脂肪和碳水。目标来自用户 Profile 的 `calorie_target`、`protein_target`；目标未设置时只展示实际摄入，不判断是否达标。

分析结果必须包含：统计范围、已纳入的明细数/总明细数、各营养值、目标对比（若有目标）、未匹配项提示和非医疗建议免责声明。报告可继续暂存于现有 `analysis_reports.report_json`，待分析功能真正实现时再决定是否规范化。

## 9. 餐食计划和购物清单

第一版限制为单用户、1-7 天、每天早餐/午餐/晚餐。输入支持人数、预算、热量目标、蛋白质目标、忌口和过敏原。Java 确定性生成器负责生成和校验；Python 只做自然语言理解和参数提取，生成后必须经过 Java 校验。

状态机：

```text
draft -> validated -> saved
```

计划修改后回到 `draft`，必须重新校验和确认；只有 `saved` 计划才能生成正式购物清单。`meal_plans` 和 `shopping_lists` 当前继续保留 JSON 结构，字段语义和状态以本节为准。

## 10. 本地可观测性、压测和故障恢复

### 10.1 本地可观测性

- Java 保留 Actuator `/actuator/health/liveness` 和 `/actuator/health/readiness`。
- 增加本地可访问的基础 metrics，用于请求数、错误数、延迟和核心异步积压的最小观察；暂不承诺 Prometheus/Grafana 格式和生产告警。
- Java/Python 日志至少包含 `request_id`、`trace_id`、`run_id`，不得记录密钥、完整 Prompt 或敏感营养/账户信息。

### 10.2 本地压测

已执行的第一轮脚本使用两个 Java JVM，共享 PostgreSQL，测量的是认证会话读取，不包含饮食记录、营养查询、计划确认、Agent 业务流量或 SSE；历史 160 请求和本轮依赖重启后的 20 请求均为 0% 错误率。本结果只作为本机读取基线，不外推生产容量。完整业务链路吞吐、数据库连接池、队列积压和重复执行数仍待单独设计并执行。

### 10.3 本地故障恢复

目标矩阵覆盖 Java、Python、PostgreSQL、Redis、RocketMQ 逐个重启，以及 Outbox/Inbox 重试、ACK 丢失、租约接管、重复消息和 SSE 恢复。当前已实际验证 Java 重启回读、Python Runtime 重启后的 readiness、Redis AOF 探针恢复、RocketMQ 组件重启/Topic 初始化，以及 MQ Outbox/Proposal/Result、DLQ、continuation 和 Java checkpoint 对账回归；尚未完成 PostgreSQL 进程重启和完整 ACK/租约/SSE 业务故障注入。允许当前请求失败，但必须满足：

- 不丢失已提交业务数据；
- 不重复执行写副作用；
- 不伪造成功；
- 恢复后可重新查询饮食记录、营养分析、餐食计划、确认事实和 SSE 事件。

数据库备份恢复不属于本轮验收。
