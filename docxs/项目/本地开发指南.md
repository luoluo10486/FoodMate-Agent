## 1. 当前边界

截至 2026-08-15，前端已完成部分真实认证、会话、AgentRun SSE 和用户业务页的代码迁移；Java 已完成本地 `local` profile 下 M1-5 核心路径，包含饮食记录创建、查询、编辑、删除、恢复、分析、5 条营养 seed 的匹配、餐食计划完整资源生命周期和 `meal_plan.save_plan` 确认，`food_log_writer` 的 create/update/delete/restore 及状态、revision、幂等回归已通过真实 HTTP/MQ；Python Agent Runtime 已存在并完成 M1-3/M1-4 的本地 deterministic stub、受控 Runtime、健康检查和跨进程链路验证。本指南中的“当前可执行”命令仍只覆盖已实际验证的入口；`local-stub` 不连接 PostgreSQL，更广泛业务 Tool/SQL 或生产级稳定性仍不可推断为已完成。

仓库已有 `docker/compose.yml` 作为本地依赖入口，但不会自动执行迁移或 seed；本轮使用 Docker PostgreSQL/Redis 和两个 Java HTTP 进程完成了 M1-6 双 JVM 子项复验。编辑回归覆盖 revision CAS、幂等重放、旧明细软删除和新明细生效；seed V1 和 V2 已另行人工执行并校验。更广泛业务 Tool/SQL 和生产级治理仍未完成。不要把下文目标态当作现有能力。

## 2. 当前可执行：前端

在仓库根目录执行：

```powershell
cd foodmate-ui
npm install
npm run dev
```

Vite 将在终端打印本地访问地址。当前多数业务页面仍使用 `src/mock` 数据；认证、部分会话/AgentRun 和记忆页面已有真实接口接入，但本地启动前端本身不会自动启动或连接 Java 后端。

### 2.1 管理后台 real 模式业务检查

需要验证管理后台真实接口时，在 Java API 已启动且当前浏览器已有 admin/operator 会话的前提下执行：

```powershell
$env:VITE_AGENT_MODE = 'real'
$env:VITE_API_PROXY_TARGET = 'http://127.0.0.1:8080'
npm run typecheck
npm run test -- --run src/pages/AdminPage/tabs/UsersTab.test.tsx src/pages/AdminPage/tabs/RunsTab.test.tsx src/pages/AdminPage/AdminPage.test.tsx
npm run dev
```

真实只读入口包括 `/api/admin/queries/runs`、`/api/admin/queries/tool-calls`、`/api/admin/queries/sql-audits`、`/api/admin/users` 和 `/api/admin/dashboard`；写操作必须由页面确认流程发出 `Idempotency-Key`、`revision` 和确认字段。接口失败或无数据时页面显示错误/空态，不使用 fixture 回退。当前后端尚无 Trace 分页资源，real 模式 Trace 维持空态。

知识库 real 管理入口使用批量上传表单（来源类型、名称、版本、授权说明和幂等键），通过 `/api/admin/knowledge-documents/upload-batches` 提交；批次详情通过 `/api/admin/knowledge-upload-batches/{batchId}` 和 SSE 进度恢复，索引失败条目可手动重试。发布、下线、恢复和删除继续走管理员确认流程，接口失败不会回退到 fixture。

### 2.2 餐食规划 real 模式业务检查

在 Java API 已启动且当前浏览器已有用户会话的前提下执行：

```powershell
$env:VITE_AGENT_MODE = 'real'
$env:VITE_API_PROXY_TARGET = 'http://127.0.0.1:8080'
npm run test -- --run src/pages/PlanningPage/PlanningPage.test.tsx src/pages/PlanningPage/PlanningPage.real.test.tsx
npm run typecheck
npm run build
npm run dev
```

页面从 `GET /api/meal-plans` 读取当前用户计划；列表按服务端状态显示进行中、草稿和已归档，进入计划后使用返回的 `days_plan` 和约束数据。没有计划时，真实空态会进入创建向导，不跳转到 Chat；接口失败时显示明确错误态，不回退到 fixture。

真实创建向导在确认步骤调用 `POST /api/meal-plans`，请求带 `Idempotency-Key`，使用向导参数生成确定性的本地餐表，不调用云模型。创建成功后按服务端返回的 `meal_plan_id` 打开详情；已保存计划会读取 `GET /api/meal-plans/{meal_plan_id}/shopping-list` 展示购物清单。重新生成仍需要通过 AgentRun 发起，未将前端本地按钮伪装成真实生成能力。

可单独执行的检查命令：

```powershell
cd foodmate-ui
npm run build
npm run lint
npm run test
```

已知基线（2026-07-11）：`npm run build` 通过；`npm run lint` 因 35 个 warning 与 `--max-warnings 0` 失败；`npm run test` 因没有匹配 `src/**/*.{test,spec}.{ts,tsx}` 的测试文件失败。失败不能作为通过门禁处理。

## 3. 当前可执行：Java stub

根 `pom.xml` 要求 Java 21 和 Maven 3.9+；优先使用仓库 Maven Wrapper：

```powershell

& java -jar '.\foodmate-bootstrap\target\foodmate-bootstrap-0.1.0-SNAPSHOT.jar' '--spring.profiles.active=local-stub'
```

`application.yml` 的默认 profile 已是 `local-stub`。该 profile 排除 DataSource 和 Flyway 自动配置，并将 `foodmate.runtime.stub-enabled` 设为 `true`。启动后在另一个 PowerShell 中检查：

```powershell
Invoke-WebRequest http://localhost:8080/actuator/health
```

上述 JAR 路径和参数已于 2026-07-11 实际验证：`package` 成功，`/actuator/health` 返回 HTTP 200 和 `UP`，进程随后已终止。日常前台运行时使用 Ctrl+C 正常停止。当前审计基线为 `.\mvnw.cmd clean verify` 通过，14 个 Maven Reactor 项目成功，Surefire 共 29 个测试、0 failure/error/skipped。该结果只证明现有骨架和测试，不证明目标态业务链路。

## 4. 真实 PostgreSQL 配置路径：本地已验证

`local`、`dev` 和 `prod` profile 均启用 DataSource 与 Flyway；当前本地验证使用 Docker PostgreSQL 16 `FoodMate` 数据库，应用不会自动执行迁移。`application-local.yml` 包含可由 `DB_URL`、`DB_USERNAME`、`DB_PASSWORD` 覆盖的本地连接配置；不要把实际密码提交到 YAML、`.env` 或日志。双 JVM 门禁脚本默认使用 `http://localhost:18080` 和 `http://localhost:18081`。

本地真实数据库结构、Java Repository、认证和 M1-5 核心 HTTP/MQ E2E 已验证；编辑回归和双 JVM 门禁均使用随机账号并在结束后软删除清理，5 条 seed 的真实营养目录 `matched` 数值也已通过 HTTP/MQ writer 回归验证。Redis/RocketMQ 重启后的本地恢复已复验，但 PostgreSQL 进程重启和完整 Outbox/Inbox/SSE 故障矩阵未完成，不应把单个业务 E2E 或本地读取基线推断为生产可用性。

### 4.1 M1-6 双 JVM 本地子项

PostgreSQL 和 Redis 已启动后，在项目根目录执行：

```powershell
.\script\local\m1-6-dual-jvm.ps1
```

脚本会在未占用的 `18080/18081` 启动两个独立 Java JVM，完成跨实例会话读取、有界 P50/P95/P99/吞吐/错误率采集，重启 `18080` 后再次读取 PostgreSQL 中的会话，并在 finally 中软删除本轮测试账号。历史 160 请求基线为 0% 错误率、51.538 req/s；依赖重启后的 20 请求复验为 0% 错误率、14.765 req/s。输出只代表本机认证会话读取基线；脚本不会启动 Python/RocketMQ，也不完成完整 M1-6 故障矩阵。

### 4.2 M1-6 本地依赖恢复复验

在 `.env` 已配置本地 PostgreSQL/Redis/RocketMQ 后，可按以下顺序启动 RocketMQ（Proxy remoting 使用 `18008`，避免与前端常用 `8080` 冲突），再启动 Python Runtime：

```powershell
$env:ROCKETMQ_PROXY_REMOTING_PORT = '18008'
docker compose --env-file .env -f docker/compose.yml up -d rocketmq-proxy
docker compose --env-file .env -f docker/compose.yml up rocketmq-init
.\.m14-start-python.ps1
Invoke-RestMethod http://127.0.0.1:9002/foodmate/internal/health/ready
```

本轮验证结果：Python readiness 为 HTTP 200，Redis、Redis checkpoint、RocketMQ event/proposal producer、command/result consumer 均为 `ready`；Redis AOF 探针在容器重启后保留；RocketMQ NameServer/Broker/Proxy 重启后 healthy，Topic/group 初始化成功。Java MQ 回归为 `M14RocketMqTransportE2ETest 1/1`、`M14ProposalResultE2ETest 2/2`、`M14RuntimeCheckpointRecoveryE2ETest 1/1`、`M14ContinuationE2ETest 3/3`、`M14DlqReconciliationE2ETest 3/3`，Python 为 `56 passed, 1 skipped`。这些结果不包含 PostgreSQL 进程重启、生产容量和完整 ACK 丢失/租约接管/SSE 恢复矩阵。

### 4.3 M1-6 流量与单故障入口

在 Java（`8080`）、Python Runtime（`9002`）和 Docker PostgreSQL/Redis/RocketMQ 已就绪后执行：

```powershell
.\script\local\m1-6-traffic-recovery.ps1
```

该命令只读取 Java Actuator、Python readiness 和 Docker Compose 状态，不发送业务流量或重启组件。它会输出带随机 `run_id` 的 JSON 预检记录。完成既有 HTTP/RocketMQ writer harness 的真实流量采集后，才可把相同记录追加到执行台账。若需要验证 Redis 单故障恢复，必须显式执行：

```powershell
.\script\local\m1-6-traffic-recovery.ps1 -EnableFaultInjection
```

该开关会重启 `redis` 容器并等待 Python readiness；不会重启 PostgreSQL、RocketMQ、Java 或 Python，其他故障场景仍须逐项执行并记录。脚本不执行迁移、truncate、备份恢复，也不会清理既有本地数据。

## 5. 当前依赖与工作方式

前端依赖由 `foodmate-ui/package.json` 定义，开发入口是 Vite；其构建包含 TypeScript 检查。Java 根工程固定 Java 21、Spring Boot 3.5.16、MyBatis-Plus 3.5.16 和 Maven Enforcer。不要自行新增 Python、Docker 或 CI 命令来替代尚未存在的工程入口。

前端与 Java 可以分别运行；M1-5 核心路径已完成本地 HTTP、Cookie/CSRF 和 PostgreSQL 业务数据联调，饮食记录编辑及 `food_log_writer` 四类写操作已覆盖真实 HTTP/MQ 回归；前端饮食记录、营养分析、知识检索和餐食规划列表/详情已有 real 主路径，规划创建向导和购物清单仍保留原型流程。开发 mock UI 时，必须把其结果视为原型行为；不能把 mock 结果标记为端到端完成。

## 6. Python Agent Runtime

当前已有独立 `agent-runtime`、`pyproject.toml`、V1 dispatch/cancel 路由、健康检查与 pytest。M1-3 使用确定性 stub；M1-4 已完成受控模型适配、Router、Planner、执行引擎、Proposal/Result 和本地恢复链路的实现与验证。2026-08-22 项目 `.venv` 全量 pytest 为 `92 passed, 1 skipped`；真实云模型长期稳定性、生产级压测和更广泛业务 Tool/SQL 联调仍未完成。

目标 Runtime 只处理推理、编排、RAG、模型调用、质量校验和回答组装。它必须通过已批准的 V1 内部契约与 Java 通信，不能使用业务数据库凭据，也不能直接读写业务表、Tool 或 SQL 执行面。

Python probe 路径固定为 `GET /foodmate/internal/health/live` 和 `GET /foodmate/internal/health/ready`。当前 Runtime 使用标准库 HTTP Server，不是 FastAPI；所有 Python health 调用必须保留完整的 `/foodmate/internal` 前缀。
