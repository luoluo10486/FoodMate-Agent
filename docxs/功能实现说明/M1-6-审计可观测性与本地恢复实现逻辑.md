# M1-6 审计、可观测性与本地恢复实现逻辑

## 1. 实现范围

M1-6 的实现目标是让业务写入、AgentRun、消息投递和 SSE 事件具有可追溯的业务事实。当前实现优先覆盖 Java/Python 本地运行时和 Docker Compose，不引入 Prometheus、Grafana、Kubernetes 或生产告警平台。

当前代码中的职责边界如下：

| 层 | 主要实现 | 责任 |
|---|---|---|
| application | `OperationAuditPort`、`OperationAuditService`、`AgentOperationMetrics` | 构造统一审计事实、脱敏摘要和低基数指标 |
| infra | `OperationAuditMapper`、运行时/知识库持久化适配器 | 在 PostgreSQL 中写入审计和技术状态 |
| api | `TraceContextFilter`、`AdminOperationalQueryController` | 建立 request/trace 关联并提供管理员查询 |
| Python Runtime | `runtime_env.py`、`runtime_server.py`、`mq_runtime.py` | 传播 Trace、报告 readiness、消费消息并维护运行统计 |
| local scripts | `m1-6-traffic-recovery.ps1`、`m1-6-fault-matrix.ps1` | 本地业务复验和受控恢复探针 |

## 2. 统一业务审计

业务用例通过 `OperationAuditService` 构造 `AuditRecord`，再调用 `OperationAuditPort`。PostgreSQL 只有 `OperationAuditMapper` 作为统一业务审计写入口。业务模块不直接操作 `operation_audits`。

审计记录保存操作者、目标、action、result、error_code、request_id、trace_id、参数摘要、结果摘要和幂等键。`OperationAuditService` 对嵌套对象执行深度、数组长度和字符串长度限制，并拒绝密码、Token、Secret、API Key、Prompt、完整回答、饮食备注和原始业务请求进入摘要。

同步业务命令在同一个事务边界写业务表、Outbox 和成功审计。统一审计写入失败会使业务事务失败。业务异常需要通过独立失败事务写入 `failed` 或 `rejected` 审计，避免失败事实随原事务回滚而消失。审计主键由共享 `IdGenerator` 提供，不使用 `MAX(id)+1`。

协议错误、事件 Inbox、SQL 查询和 Outbox/Inbox 技术状态继续使用各自专用记录；它们不会重复伪装成业务审计。

## 3. Trace 与指标

`TraceContextFilter` 为每个 HTTP 请求建立或接收 `request_id`、`trace_id`，并同步到 MDC。Runtime Command、Event、ToolCall、Model Usage、SQL Audit、Operation Audit 和 SSE Outbox 都保留关联 Trace。

管理员查询入口为 `/api/admin/operations/{resource}`，Trace 明细入口为 `/api/admin/operations/traces/{traceId}`。`AdminOperationalQueryMapper` 只返回跨度类型、名称、服务、状态、时间、耗时、错误码和序号，不返回 Prompt、消息正文、SQL 原文、对象键或供应商凭据。Trace 跨度由以下事实投影：

- `runtime_event_inbox_v2`：Python Runtime 事件。
- `tool_calls`：工具调用。
- `model_usage_logs`：模型调用和用量。
- `agent_run_sse_outbox`：SSE 事件。
- `sql_query_audits`：SQL 审计。
- `operation_audits`：业务审计。

`AgentOperationMetrics` 只允许 `transport`、`operation`、`result`、`reason` 四类标签，覆盖 dispatch、proposal、result、event、SSE replay、知识索引、可见性和清理任务。用户 ID、Run ID、Proposal ID 和消息 ID 不进入指标标签。请求延迟使用 Timer 或有界快照统计，不能从指标标签重建个人数据。

Python readiness `/foodmate/internal/health/ready` 报告 checkpoint、Redis、RocketMQ producer/consumer 和受控运行统计。协调依赖不可用时返回结构化的 `RUNTIME_COORDINATION_UNAVAILABLE`，不会伪装成健康。

## 4. 本地验证入口

本地 Docker 业务流量入口使用 `m1-6-traffic-recovery.ps1`。它只生成随机命名空间测试账号，结束时软删除本轮账号，不执行 `truncate` 或数据库硬删除。队列快照区分可排空 Outbox/Inbox 与保留的 SSE 事实；SSE 历史保留不被错误计为积压。

故障矩阵入口使用 `m1-6-fault-matrix.ps1`，容器目标有显式 allow-list，并要求显式 `-Execute`。可验证 Java、Python、PostgreSQL、Redis、RocketMQ 重启，Outbox/Inbox ACK 丢失、重复 Proposal/Event 和 `Last-Event-ID` 回放。所有场景记录组件、注入时间、恢复时间、重试次数、业务写入、审计数量、重复副作用和 SSE 缺口。

截至 2026-09-01，执行记录已包含 Docker Runtime 双 Embedding、M1-6 本地业务流量和 M3 本地备份恢复证据。性能容量、生产监控告警、生产部署和生产回滚不能由这些本地结果推导。

## 5. 排障顺序

1. 先检查 Java `/actuator/health/readiness` 和 Python `/foodmate/internal/health/ready`。
2. 根据 `request_id`、`trace_id`、`agent_run_id` 查询 Trace 明细。
3. 查看 Runtime dispatch、Inbox、SSE Outbox 的状态和错误码。
4. 核对对应的业务审计是否存在，确认是否为业务拒绝、业务失败或基础设施错误。
5. 仅对明确允许的本地容器执行单组件恢复，恢复后再次检查业务事实和幂等结果。

## 6. 安全边界

真实云 API Key 只从本地忽略 `.env` 或 Secret Store 注入，不进入 Git、执行记录、Trace 响应或日志。`security-scan.ps1` 检查 tracked 文件和普通工作树文件，允许本地忽略 `.env` 保存开发密钥但不会把它加入提交。`secret-rotation-check.ps1` 负责验证服务 JWT、RAG 和 Chat 配置是否满足分离和 fail-closed 条件；供应商控制台中的实际密钥轮换仍必须由运维人员执行并取得外部证据。
