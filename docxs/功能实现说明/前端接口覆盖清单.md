## 1. 文档目的

本清单以当前工作树中的 `foodmate-api` Controller 源码为唯一后端路径来源，以 `foodmate-ui/src/services` 和页面调用为前端接入来源。它记录接口是否已经被前端 service 封装，不把 mock Fixture、页面静态展示或“存在 Controller”当成真实闭环完成。

当前执行边界：

## 10. 关键契约规则

### 10.1 统一 HTTP 边界

- JSON 请求统一经过 `foodmate-ui/src/services/apiClient.ts` 的 `apiRequest`。
- 非安全方法自动携带 `credentials: include` 和 `X-CSRF-Token`。
- 401 只触发一次 refresh；refresh 失败后清理本地登录缓存并跳转登录页。
- 403、网络失败、业务错误码和空响应不能被 service 静默吞掉。
- 上传接口保留 `FormData`，不能手工设置 multipart boundary。

### 10.2 JSON 命名

- 明确使用 `@JsonNaming(SNAKE_CASE)` 的后端 DTO：恢复请求、会话、饮食记录、餐食计划和保留策略等使用蛇形字段。
- 未声明 `@JsonNaming` 的后端 DTO：预算追加、取消、审批、模型治理和部分 Admin 写请求使用 Java 默认驼峰字段。
- SSE payload 的领域字段以事件协议为准，不能按页面变量名随意重命名。

### 10.3 写入与幂等

- `revision` 是后端乐观锁事实，前端不得固定写死并吞掉冲突。
- 需要幂等键的写操作由 service 生成唯一键；用户重试必须保持业务动作独立，不能把 HTTP 200 接受响应当成业务完成。
- Agent 写入必须遵循 `proposal -> confirm/reject -> execute`；只有 execute 返回后才能刷新业务数据。
- Admin 高风险写操作使用后端约定的确认摘要；摘要算法只用于构造请求，最终有效性由后端校验。

### 10.4 SSE

- 页面保留已显示文本，重连使用最后一个服务端事件 ID。
- `sse_event_id`、SSE message ID 和业务事件 ID 按 service 层规则去重。
- `completed/failed/cancelled/superseded` 是终态；收到终态后关闭连接。
- 组件卸载、会话切换和用户取消必须关闭连接和定时器。
