# M3 数据保留、安全治理与恢复实现逻辑

## 1. 实现边界

M3 当前实现的是可审计、可回滚和默认关闭的治理能力。它不把本地 Docker 证据解释为生产部署、生产灾备或生产发布回滚。任何不可逆操作都必须通过策略、应用开关、备份校验和管理员审批的多重门禁。

## 2. 数据保留与清理任务

Java `DataRetentionService` 负责保留策略、legal hold、争议冻结、审批和清理任务状态；`DataRetentionTaskPublisher` 负责将已批准任务投递给数据库、对象存储和向量清理后端；`DataRetentionResultMessageProcessor` 以幂等方式消费 Python 向量清理结果。

清理顺序固定为业务关联事实、对象存储对象和向量索引，避免孤儿数据。任务领取 SQL 同时检查 active legal hold，并使用 lease 防止多个执行者重复领取。每个结果保存 backend、删除数量、缺失校验、错误码和安全摘要。重复结果不会产生第二次业务副作用。

数据库清理适配器 `DataRetentionDatabasePurgePort` 只在以下条件全部满足时可执行：

1. 策略记录的 `hard_delete_enabled=true`。
2. `FOODMATE_RETENTION_EXECUTION_ENABLED=true`。
3. `FOODMATE_RETENTION_EXECUTION_BACKUP_VERIFIED=true`。
4. 任务已经完成管理员审批，且不存在 active hold。

默认配置关闭执行器，因此普通启动不会领取或删除任何数据。应用失败时任务进入可解释失败状态并保留重试/DLQ 事实。

## 3. 数据库硬删除与备份恢复

`script/sql/FoodMate/backup-restore.ps1` 支持 Docker 内 PostgreSQL 的自定义格式备份、隔离库恢复、`validation.sql` 校验和验证后删除恢复库。脚本拒绝覆盖已有备份或恢复库，并要求恢复目标与源库不同。备份文件放在 Git 忽略目录，不上传仓库。

`DataRetentionDatabasePurgeRealIntegrationTest` 使用独立 PostgreSQL 容器验证知识文档及关联 chunks、索引/事件事实的依赖顺序删除和幂等重复执行。该测试不连接现有业务库，也不改变本地生产数据。

本地执行顺序：

```powershell
.\script\sql\FoodMate\backup-restore.ps1 `
  -DatabaseName FoodMate `
  -Username postgres `
  -DockerContainer foodmate-postgres `
  -BackupFile codex_local_foodmate_<utc>.dump `
  -RestoreDatabaseName codex_restore_<utc> `
  -Execute -RunValidation
```

只有在恢复库校验成功后，才允许使用 `-DropRestoreDatabaseAfterValidation` 清理本轮隔离恢复库。不得对当前源库使用 `R1__drop_core_schema.sql` 或任何未经审批的宽泛删除脚本。

## 4. DLQ 与运营审计

DLQ 保存消息来源、消费者组、消息 ID、关联 Run/Dispatch/Event ID、尝试次数、错误码和对账状态，不保存完整消息载荷。管理员只能查询安全摘要或通过受控入口人工重放；重放会建立新的 Outbox 事实并保留原始关联，不能直接修改消费状态。

`AdminAuditReportService` 提供实时只读快照，聚合统一操作审计、运行时/知识/SSE Outbox、索引条目和 DLQ 的数量、最早时间、稳定原因码及 `passed/attention` 状态。报告不返回请求 JSON、消息载荷、Prompt、完整回答或错误堆栈。历史归档、自动告警和生产通知系统仍需独立建设。

## 5. 安全扫描与密钥轮换

`security-scan.ps1` 扫描 Git 跟踪文件和普通工作树文件中的高置信凭据模式，并检查被跟踪的环境文件；本地忽略 `.env` 可以保存开发密钥，但不会被加入 Git。扫描输出只包含计数，不输出匹配内容。

`secret-rotation-check.ps1` 校验服务 JWT 公钥环、当前 `kid`、RAG/Chat 凭据分离、Embedding endpoint/model、Milvus、预算和价格版本。真实密钥轮换仍必须在 SiliconFlow 或其他供应商控制台执行，然后在本地更新 Secret Store/忽略 `.env`，重新创建依赖容器，运行 smoke 和安全扫描。轮换前的旧密钥不得写入执行记录；曾经在聊天或日志暴露过的密钥应视为失效并立即轮换。

## 6. 发布与回滚

数据库增量回滚只能使用对应 `rollback/R*.sql`，且必须先完成备份校验、确认没有已提交数据依赖新结构，再回滚并执行 `validation.sql`。应用容器回滚应使用已登记的旧镜像 digest 和同一 Compose 配置，不允许用源码目录覆盖运行容器。回滚结果要记录镜像 digest、迁移版本、健康检查、业务 smoke 和数据恢复结论。

当前仓库提供的是回滚前置说明和数据库反向脚本，不具备连接生产发布平台的能力；因此不能宣称生产发布回滚已完成。

## 7. 已有证据与未完成项

截至 2026-09-02，已有本地证据包括：隔离 PostgreSQL 硬删除测试通过、Docker PostgreSQL 备份/隔离恢复和 `validation.sql` 通过、默认清理门禁生效、秘密扫描和本地轮换预检通过，以及两个 SiliconFlow Embedding profile 的 Docker 协议 smoke 通过。Docker `agent-runtime` 当前已确认由 `python runtime_server.py` 启动并通过 live/readiness；本地 JWT 开关关闭，因此 JWT 重叠轮换检查未执行。

以下事项仍不能由本地证据代替：生产数据库硬删除授权、生产备份保管与灾备恢复、跨环境迁移、生产告警通知、渗透测试、供应商控制台密钥轮换确认、生产镜像发布和真实发布回滚演练。它们应在相应真实环境具备后单独取得执行记录。
