## 3. Java 单元、集成与 Testcontainers

保持当前 `.\mvnw.cmd clean verify` 作为骨架基线。后续数据库和 V2 工作必须新增真实 PostgreSQL Testcontainers，而不是只断言迁移 SQL 文本。Testcontainers 验收至少包含：

- 空库从 V1 升级到 V2、带代表性 V1 数据升级到 V2，以及 Flyway `migrate`/`validate`。
- V2 阶段 1-4 的可空新增列与上一兼容 Java 版本的读写 smoke test。
- dispatch 的 partial unique 单 active、active/admission epoch、fencing token、旧 dispatch 拒绝和事务回滚。
- `runtime_dispatch_outbox` 的 `outbox_id/dispatch_id/FK` 唯一、状态/lease CHECK、领取索引，以及 AgentRun/dispatch/immutable RunCommand outbox 同事务原子性；提交后不得从可变业务状态重建 payload。
- dispatch publisher 故障注入：提交后发送前崩溃、发送后 ACK 前崩溃、lease owner 崩溃、多实例竞争、deadline 过期、同 dispatch hash 冲突和 superseded 不发送；每次重放 payload/hash 不变，Python 业务执行计数始终为 1。
- `runtime_event_inbox` 只接受 canonical event：`(agent_run_id,event_id)` 与 active `(dispatch_id,event_seq)` 唯一；同 seq 不同 event、旧/superseded dispatch、乱序和 gap 只写无冲突唯一键的 `runtime_event_rejections`，并返回稳定 RuntimeError。
- 取消/admission epoch 与完成/失败终态竞争，首个 Java 合法终态不回退；旧 epoch/fence invocation 在副作用提交前被拒绝。
- Tool/SQL 的 `invocation_id` 与 `(agent_run_id,idempotency_key)` 幂等，`pending/leased/succeeded/failed/unknown` CHECK、owner token CAS、lease 过期安全接管，以及恶意 SQL、越权 schema、限行、超时和审计断言。
- SSE transactional outbox 的 `source_event_key/sse_event_id/(agent_run_id,stream_seq)` 唯一、业务事务原子性、publisher lease/retry/dead-letter、崩溃接管和 `Last-Event-ID` 恢复。
- `model_call_id`、provider attempt 去重和 V1 `request_id` 兼容。

当前 POM 没有 Testcontainers 依赖；在依赖、容器可用性和测试 profile 落地前，不能声称上述集成测试已运行。V2 阶段 4 启用 Runtime/Tool/SQL/SSE 主链路前，上述表、字段、索引、约束和 fixtures 必须全部通过，不能留作后续增量。

## 4. 双运行时契约与故障注入

V1 内部契约落地后，以 JSON Schema 或等价严格 DTO 校验覆盖 RunCommand、RunEvent、CancelCommand、ToolProposal/Result、SqlProposal/Result、RuntimeError 与 PreRunProtocolError。每个消息验证 `v1`、snake_case、字符串 ID、UTC 时间、未知顶层字段拒绝、RFC 8785 JCS + SHA-256 摘要、幂等键和错误码映射。

Java Runtime Client 的 MockWebServer 或统一 WireMock 测试应注入并验证：connect/read/run timeout、503、连接重置、重复 dispatch、取消重试、401/403/400/409 不重试、426 版本不兼容、PreRun 协议错误与流内 `runtime.error`。RunCommand 网络重试必须发送 outbox 中完全相同的完整 envelope（包括 body 内 `request_id/trace_id`），只刷新短期 Service JWT 等 HTTP Header；其他消息仍按契约复用业务幂等标识并可刷新 request ID。所有重试不得越过 `deadline_at`。

dispatch outbox 的 PostgreSQL Testcontainers + Runtime stub 测试必须逐项断言：只有可验证的接受/已接受 2xx 才转 `delivered`；传输不确定恢复为原 outbox 重试；deadline 和 superseded 在 POST 前转 `expired`；`RUNTIME_DISPATCH_IDEMPOTENCY_CONFLICT` 转 `failed` 且不自动创建 dispatch；显式重新派发先 supersede 旧 dispatch，再创建新 `dispatch_id/attempt/outbox`。启动恢复和并发 publisher 必须证明 lease/CAS 单领取，ACK 丢失重放由 Python `dispatch_id/request_hash` 去重，不能只断言 HTTP 调用次数。

## 5. Python Runtime 测试

当前 `agent-runtime/` 已有 `.venv`、`pyproject.toml` 和 Runtime 回归，可执行 `cd agent-runtime; .\.venv\Scripts\python.exe -m pytest -q`。2026-08-13 实测结果为 `56 passed, 1 skipped`；另已实际启动 RocketMQ + Redis Runtime，readiness HTTP 200，Redis AOF 探针和 RocketMQ 组件重启恢复通过。这仍不能证明生产云模型稳定性、生产容量或完整业务故障矩阵。

M1-4 测试必须新增并覆盖：

- 本地 RocketMQ 单 NameServer/Broker 启动、Topic 初始化、消息持久化和 Broker 重启恢复。
- Java PostgreSQL Outbox 提交后崩溃、Relay 发布重试、Broker ACK 丢失和相同 message ID/hash 重发。
- Python Redis Inbox/Event Outbox、checkpoint 原子写入、消费重复、Redis 中断停止消费和恢复。
- Java 消费事务提交后 ACK 前崩溃、MQ 重投、PostgreSQL Inbox 去重和 AgentRun 不重复推进。
- `run_id` 局部顺序、不同 Run 并行、同 Run `event_seq` gap/rejection，以及 MQ 顺序不能绕过状态机。
- retry/DLQ、不可重试 rejection 和 DLQ Reconciler 对账；DLQ 不得自动把 AgentRun 标为 failed。
- LangGraph 每条白名单边、循环预算、总节点数、模型调用数和预算耗尽终止。
- 用户 2 Session、全局 20 Run、队列 100 的可配置边界，以及 lease 过期、取消释放、priority burst、aging 和 Redis 故障关闭。
- queue、execution、node、waiting_user、cancel drain 超时各自独立计时和 `TimeoutSnapshot` 恢复。
- 70%/85%/100% Token 与成本降级、模型路由策略、用户预算追加 revision 和幂等确认。
- 最近 8 条原始消息、第 9 条触发摘要、Token 裁剪和摘要失败降级。
- Redis checkpoint 的 CAS 冲突、TTL、大小限制、加密、崩溃恢复及恢复前 Java 对账；不得重复 Tool/SQL 副作用。
- 确定性 Eval、复杂/高风险强制 LLM Judge、低风险抽样、Eval 前正文不可见、重写/重规划上限和无人审核安全降级。
- Eval 通过后的 150ms/2048 字节分片、非逐 Token 发布、稳定 event ID/seq 和 SSE 断线恢复。
- continuation 新 Run 与工具/预算恢复原 Run 的分流，以及 `superseded` 契约升级后的状态和事务测试。
- Trace 脱敏、禁止 Chain-of-Thought/完整 Prompt/默认原始响应落盘，以及用户反馈只进入离线审核集。

Python 测试还必须覆盖模型/RAG adapter、Prompt/评测离线 golden、Schema fixture、Service JWT、事件序列和 Tool/SQL proposal，并证明 Runtime 不持有业务数据库凭据、不能直接执行 Tool 或 SQL。

目标 Runtime 的路由契约测试还必须覆盖 `GET /foodmate/internal/health/live` 和 `GET /foodmate/internal/health/ready`，并拒绝任何缺少 `/foodmate/internal` 前缀的 Python health 路由。readiness 只断言实例可安全认证、接收和持久化请求；单个 run gap、duplicate conflict、lease backlog 与 outbox lag 另作业务告警和发布/灰度门禁测试，不能通过摘除恢复事件入口来“恢复” readiness。

当前缺少的是上述 M1-4 生产编排实现及其测试，不是 Python 工程本身。

## 6. E2E 与质量门禁

M1-3 已具备登录、会话、发送消息、确定性 Runtime stub、AgentRun 流式事件、取消和断线恢复的真实主链路；应保留其浏览器 E2E 证据。M1-4 还必须增加协调 503、排队/超时、预算确认、continuation、Eval 前缓冲和安全降级；Tool/SQL 确认与 RAG 在对应能力实现前不得创建“通过”的替代结论。

M1-5 业务 E2E 当前已通过：手工创建饮食记录 -> 无目录时 `pending` -> 查询 -> 当天/7 天/30 天分析 -> 计划校验/保存 -> 购物清单 -> `meal_plan.save_plan` Proposal/Confirm/Execute；数据库中已确认 `approval.propose`、`approval.confirm`、`approval.execute` 各一条成功审计。编辑已通过 service/controller 定向测试和真实 PostgreSQL HTTP 回归，回归覆盖幂等重放、revision 冲突、旧明细软删除和新明细生效。仍需补齐真实营养目录匹配/单位换算、更多 `revision` 冲突、拒绝/失败/事务回滚和完整 Tool Gateway。

M1-6 当前已完成两个独立 Java JVM 共享 PostgreSQL 的有界认证会话读取基线和 Java 重启后的数据回读，并完成 Python readiness、Redis AOF 探针恢复和 RocketMQ 组件重启恢复；该子项不包含 Agent 业务流量。完整故障测试仍要求逐个重启 Java、Python、PostgreSQL、Redis、RocketMQ，并注入 Outbox/Inbox ACK 丢失、租约接管、重复消息和 SSE 恢复；当前尚未完成 PostgreSQL 进程重启和完整业务故障注入。数据库备份恢复当前明确不在范围内。

生产级压测、多实例吞吐、云模型长期稳定性、账单审计、完整监控和发布回滚属于后置阶段，不能从本地测试结果推导完成。

建议门禁分层如下：

1. 每次前端变更：typecheck/build、lint、单元测试均为 0 退出码。
2. 每次 Java 变更：`.\mvnw.cmd clean verify`，并对迁移/持久化改动运行 PostgreSQL Testcontainers。
3. 每次契约改动：Java/Python 两端 Schema fixture、canonical digest、JWT 和错误映射互测；所有文档 JSON 示例程序化解析并按字段集重算摘要。
4. 每次发布候选：兼容矩阵、包含 dispatch outbox 的 PostgreSQL V2 reliability fixtures、上述七类派发故障注入、双运行时无双执行 smoke、迁移回滚/drain 演练和浏览器 E2E。

在现有 lint/test 失败、没有容器验证或目标 Runtime 能力尚未实现时，相应门禁状态必须是失败或不可执行，而非豁免通过。当前 3 个 Python stub 测试通过只计入 M1-3 基线。
